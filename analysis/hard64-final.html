Is it the 5-result cap?

WorkBench’s searches return at most 5 records. On 25 of the 64 tasks the main action (deleting, reassigning, moving) is needed more than 5 times, so no single search can list every record: we call these cap-bound. If the teams only win because a second agent searches again after the first one’s changes, their lead should sit on the cap-bound tasks and vanish on the other 39.

Against the open-weight models, by size

Mixture-of-experts models use only some of their parameters for each token; “active” is that share, and it drives compute per token, while the total sets how much memory the weights need. gpt-oss-20b fits on one of the cluster’s 46 GB L40s, and the three-agent teams share that one server, so the teams cost three times the tokens, not three times the weights. The published models ran in WorkBench’s own single-agent harness, one run each. Our teams average about 4 of the 27 tasks against their 3, which one run of theirs can’t separate, so read this as “level with open models up to 76 times its size”, not “better than them”.

What the three agent-driven teams do

All three run the same harness (agent_driven.py) and differ only in which communication tools they get. Unlike the paper’s four setups there are no rounds, no orchestrator, no summaries passed on by the harness, and no vote.

Three peers, one request

agent_1, agent_2 and agent_3, all gpt-oss-20b on the same vLLM server, get the user’s request at the same moment and run at the same time, each in its own tool loop.

One shared workspace

One copy of WorkBench’s email, calendar, CRM, project board and analytics, with all 27 of its tools. A change made twice happens twice. The team is scored on how that one workspace ends up.

Nobody in charge

No roles or plan are given. Teammates’ changes notify no one: an agent sees them only in what its own tool calls return.

Sleeping and waking

An agent’s turn ends when it replies without calling a tool. Anything sent to it is added to its conversation after its current tool call, or wakes it if it is asleep. The run ends when all three are asleep with nothing in flight, or at 30 model calls per agent, 12 per wake, or 15 minutes.

How each system fails

Each task-run sorted by comparing its changes with the correct ones, averaged over the ten runs. “Stopped at the 5-result cap” means the main action (deletions, updates) was done exactly 5 times when more were needed: WorkBench’s search tools return at most 5 records.

Published column: all 1,536 runs of the 24 models on these 64 tasks. WorkBench’s 2026 write-up names the cap failure itself: “When five … come back, the model assumes it has seen them all and stops, rather than re-querying.” In our traces the single agent trusts the first 5 and replies “All of Lena’s leads have been deleted”; the orchestrator setups instead fail by adding changes nobody asked for.

How the shared-workspace teams get past the cap

When agents share one workspace, a second agent’s search runs after the first agent’s deletions and returns the next 5 records, so the team gets past the cap without anyone planning it. Communication decides whether that turns into duplicate work, and it also makes agents divide the task, which removes many of those second searches.

Got past the cap: tasks per run where the system made more than 5 of the main action, of the 25 tasks needing more than 5. Duplicate work: tasks per run where two or more agents changed the same record or chart. Means of ten runs, except the last column (first run). With no channels, agents get past the cap most often (18 of 25) and duplicate the most work (11 tasks); text messages cut duplicates to 8 but also get past the cap less often (12), so on 5+ tasks the two teams score about the same (14% and 16%).

How independent are the agents’ mistakes?

From the first run. For the two setups whose workers each act in a private copy, each worker’s changes scored on their own. More agents only help a vote if some of them are right when others are wrong.

The last column takes any two workers on the same task: of the pairs where at least one was wrong, how often were both wrong, against what independent mistakes would give at the same error rate. On small tasks decentralized’s vote always reached the “at least one right” ceiling; on these tasks it falls 7 points short, and independent’s union of everyone’s changes falls 14 short.

What this says

  1. Over ten runs, decentralized debate is the best system.It averages 44% against the single agent’s 28%, leads on tasks needing 3–4 changes (65%), and ties the agent-driven teams on 5+ tasks (15%).
  2. One run per system was not enough.The first night put the agent-driven text team on top at 42%. Its ten reruns average 35% and never reach 42%; a single run on 64 tasks moves by several points either way.
  3. Free communication in a shared workspace adds little.Text messages add 1 point over the same team without channels, inside the run-to-run noise; offering all three channels adds 5, mostly on tasks that aren’t cap-bound. What messages change most is how the work is divided: fewer duplicates, and fewer accidental second searches.
  4. The teams’ 5+ gain comes from the 5-result cap.On the 25 cap-bound tasks the single agent never succeeds, and the shared-workspace teams reach 10–13% largely because someone searches again after records were changed. On the other 39 tasks the no-channels team is no better than the single agent.
  5. Part of the gap is the single agent’s prompt.One agent working alone with the independent setup’s “work thoroughly and systematically” prompt solves 56% of the tasks that aren’t cap-bound, against 46% for our single agent. A single agent with that prompt, and one told to search again until a search returns fewer than 5 results, are the controls to run next.
  6. Orchestrators hurt.Centralized and hybrid score 18%, below the single agent, at 6–8 times its tokens, mostly by applying changes nobody asked for (21–23 tasks per run).
