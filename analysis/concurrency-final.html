        How the log works

        Every agent on the team reads and writes one append-only log. The harness enforces the order of operations; the agents decide what to do about what they see.

        1. Read the logwal_read returns every intent and change the agent hasn't seen yet.
        2. Post an intentwal_append: a plan plus each resource it will change and how, e.g. update crm "00000187".
        3. Make the changeThe write runs and is added to the log automatically, with its outcome.
        • A post is refused while the agent has unread entries, and the missed entries are shown instead. Of two agents planning at the same moment, the second always sees the first's intent.
        • A write is refused if the agent has unread entries, has posted no intent, or its latest intent doesn't declare that resource and operation (create, update or delete).
        • The check, the write and its log entry happen as one atomic step, so an agent can only write once it has been shown every earlier entry.
        • Nobody is notified of new entries, and the log blocks nothing on its own: it guarantees agents see each other's work, not that they act on it.

        What the log leaves open

          Closing the rest: checking targets, not just operations

          Today the log checks that an agent has seen everything and declared the kind of change. Two further checks would compare the change itself with teammates' logged changes, either warning the agent or refusing unless it gives a reason.

            The paper's topologies: private copies

            In independent, centralized, decentralized and hybrid, each worker changes only its own copy of the workspace, so there are no write conflicts to remove. The log only tells each worker what the others are doing. What that does depends on how the team combines its work.

              Definitions and data

              • Task-run: one task in one run. Each setup has 10 runs of the same 64 WorkBench tasks whose correct answer makes 3 or more changes (640 task-runs). Teams have 3 agents on gpt-oss-20b.
              • Duplicate insert: two agents each created the same thing: an email with the same recipient and subject, a reply or forward of the same email, an event with the same name and start, a customer or task with the same name, or the same plot.
              • Write to a deleted record: a write that failed with "not found" because a teammate had already deleted that record.
              • Redundant write: a write that changed nothing because a teammate had already made the same change to that record.
              • Lost update: two agents set the same field of the same record to different values; the later one wins.
              • Conflicts are counted only for the agent-driven teams, where all agents share one live workspace. Scripts: analysis/concurrency.py (this page's numbers), analysis/conflicts.py, analysis/wal_compare.py; the log itself is wal.py.
