Is it the 5-result cap?

WorkBench’s searches return at most 5 records. On 25 of the 64 tasks the main action (deleting, reassigning, moving) is needed more than 5 times, so no single search can list every record: we call these cap-bound. If the teams only win because a second agent searches again after the first one’s changes, their lead should sit on the cap-bound tasks and vanish on the other 39.

Against the open-weight models, by size

Mixture-of-experts models use only some of their parameters for each token; “active” is that share, and it drives compute per token, while the total sets how much memory the weights need. gpt-oss-20b fits on one of the cluster’s 46 GB L40s, and the three-agent teams share that one server, so the teams cost three times the tokens, not three times the weights. The published models ran in WorkBench’s own single-agent harness, one run each; 6 tasks against 3 is within the noise of a single run on 27 tasks, so read this as “level with open models up to 76 times its size”, not “better than them”.

What the three agent-driven teams do

All three run the same harness (agent_driven.py) and differ only in which communication tools they get. Unlike the paper’s four setups there are no rounds, no orchestrator, no summaries passed on by the harness, and no vote.

Three peers, one request

agent_1, agent_2 and agent_3, all gpt-oss-20b on the same vLLM server, get the user’s request at the same moment and run at the same time, each in its own tool loop.

One shared workspace

One copy of WorkBench’s email, calendar, CRM, project board and analytics, with all 27 of its tools. A change made twice happens twice. The team is scored on how that one workspace ends up.

Nobody in charge

No roles or plan are given. Teammates’ changes notify no one: an agent sees them only in what its own tool calls return.

Sleeping and waking

An agent’s turn ends when it replies without calling a tool. Anything sent to it is added to its conversation after its current tool call, or wakes it if it is asleep. The run ends when all three are asleep with nothing in flight, or at 30 model calls per agent, 12 per wake, or 15 minutes.

How each system fails

Each task-run sorted by comparing its changes with the correct ones. “Stopped at the 5-result cap” means the main action (deletions, updates) was done exactly 5 times when more were needed: WorkBench’s search tools return at most 5 records.

Published column: all 1,536 runs of the 24 models on these 64 tasks. WorkBench’s 2026 write-up names the cap failure itself: “When five … come back, the model assumes it has seen them all and stops, rather than re-querying.” In our traces the single agent trusts the first 5 and replies “All of Lena’s leads have been deleted”; the orchestrator setups instead fail by adding changes nobody asked for.

Why the shared-workspace teams win on 5+ tasks

When agents share one workspace, a second agent’s search runs after the first agent’s deletions and returns the next 5 records, so the team gets past the cap without anyone planning it. Communication decides whether that turns into duplicate work.

Got past the cap: tasks where the system made more than 5 of the main action, of the 25 tasks needing more than 5. Duplicate work: tasks where two or more agents changed the same record or chart. With no channels, agents get past the cap most often but duplicate the most work; text messages keep most of the benefit and cut duplicates from 13 tasks to 5.

How independent are the agents’ mistakes?

For the two setups whose workers each act in a private copy, each worker’s changes scored on their own. More agents only help a vote if some of them are right when others are wrong.

The last column takes any two workers on the same task: of the pairs where at least one was wrong, how often were both wrong, against what independent mistakes would give at the same error rate. On small tasks decentralized’s vote always reached the “at least one right” ceiling; on these tasks it falls 7 points short, and independent’s union of everyone’s changes falls 14 short.

What this says

  1. On hard tasks, teams beat the single agent.Decentralized and the agent-driven text team reach 41–42% on all 64 against the single agent’s 27%, the reverse of the small tasks, where the single agent matched or beat almost every team.
  2. Agent-driven messaging is the most efficient team.The text team ties decentralized at 193k tokens per task against 339k, and leads on 5+ tasks (22% against 11%).
  3. Orchestrators hurt.Centralized and hybrid score 17%, below the single agent, at 7–8 times its tokens, mostly by applying changes nobody asked for.
  4. The 5+ gain rests partly on a tool quirk.Teams get past the 5-result cap because a second agent searches after the first one’s deletions. A single agent told to keep searching until a query returns fewer than 5 results is the comparison that separates “more agents” from “search again”.
  5. Mistakes are still highly correlated.Three copies of the same model mostly fail together, which caps what voting or debate can recover; checks against the workspace don’t depend on that.
